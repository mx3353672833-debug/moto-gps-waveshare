# RouteBundle protocol

The Bluetooth Low Energy contract between the phone and the ESP32 uses versioned binary frames,
see [`ble-navigation-v1.en.md`](ble-navigation-v1.en.md). It defines the fixed GATT UUIDs, the
display snapshot, local route geometry, traffic/off-route state, media state, device commands,
fragmentation, CRC, ACK and timeouts; the implementation and the golden test vectors are in
`shared/ble_protocol` and `fixtures` respectively.

## Network RouteBundle

`route-request.v1.schema.json` and `route-bundle.v1.schema.json` are the level-B network contract
shared by the Web and the ESP32. Raw Provider fields must not cross the backend; both ends
decode the response into the same C++ `RouteBundle`.

`route-options.v1.schema.json` is the candidate route envelope used before the phone starts
navigation, containing at most three `RouteBundle` objects with the same structure. It only
handles the app's overview and selection; after the user confirms, the selected one still enters
the navigation core through the existing RouteBundle/Bluetooth protocol, and the firmware does
not need to hold three long routes at the same time.

`map-scene.v1.schema.json` is the local rolling-window contract between the offline map generator
and the app: at most 24 roads / 192 road points and 16 buildings / 128 building points. It is not
a server API, and it does not mean the whole-Jinan data has already been generated; the
corresponding BLE binary message is `MapScene (0x14)`.

## Coordinate boundary

- Route request origins and destinations are always marked `WGS84`, consistent with the raw GNSS
  output.
- The AMap Provider converts the request points to `GCJ-02` at the backend boundary and then
  calls AMap.
- Routes returned by AMap stay `GCJ-02`, and the response also explicitly marks
  `coordinate_system: "GCJ-02"`.
- Before route matching the device must convert WGS84 position samples to GCJ-02 through the
  shared conversion function of the same version. Data without a coordinate mark must not be
  passed into the protocol layer.

On the C++ side this boundary is enforced with the strong types `Wgs84Point` and `Gcj02Point`,
which do not implicitly convert to each other: raw GNSS and `RouteRequest` may only use the
former, and `RouteBundle.polyline` and projection matching may only use the latter. The
navigation core keeps both the raw WGS84 fix and the converted GCJ-02 match fix, so a reroute
request does not send shifted coordinates by mistake.

In v1 a destination still has to be WGS84. AMap POI search is already integrated: the app/web
page passes the phone's WGS84 position to the gateway as a nearby search bias, the Provider
calls AMap with GCJ-02, and the gateway then explicitly converts the result entry point back to
WGS84 before returning it to the client. The route request then only accepts this marked WGS84
destination, and disguising a raw AMap GCJ-02 POI coordinate as WGS84 is forbidden.

The AMap route is not approximately converted back to WGS84 here, because the inverse conversion
would introduce another set of errors and test boundaries. If the server later starts to deliver
WGS84 routes, the protocol version must be raised; the meaning of v1 must not be changed
silently.

## Out-of-order and stale responses

`request_id` is a 32-bit non-zero monotonic number generated by the client. The gateway echoes
it unchanged in success and error responses, but the gateway does not decide for the client which
request is still valid:

1. The navigation core records the number of the route request currently in flight.
2. After a new off-route reroute is issued the old request is immediately invalid.
3. On a response, the route is atomically replaced only when `request_id` equals the currently
   active number; other responses are discarded.

That way a stale request completing after a newer one cannot switch the vehicle back to the old
route.

## Version rules

- The outer `protocol_version` governs network packets, request correlation and error semantics.
- The inner `route.schema_version` governs route fields and encoding.
- A v1 parser must reject unknown required versions and out-of-range arrays; it must not assume
  Provider default values when fields are missing.
- Adding optional fields may keep v1; changing the coordinate system, units, field meaning or
  deleting a field must raise the version.

The current v1 uses readable JSON, which makes feasibility validation easier. If real-hardware
testing shows that the transfer or parse memory exceeds budget, a binary v2 can be added; until
then the web page and the firmware both use this contract and the functional behaviour does not
fork.
